# 模型调用层

`agent/AgentClient.kt`。四个任务共用它，每次调用相互独立、不共用上下文。

## 端点不写死在代码里

任何说 **OpenAI 兼容** 或 **Anthropic Messages** 协议的服务都能接：
GLM、Kimi、MiniMax、海内外中转站、局域网里的 Ollama。一个端点 =
名称 + 地址 + 协议 + Key。预置六个（Anthropic、智谱 GLM、Kimi、DeepSeek、
MiniMax、本地/局域网），URL 与 Key 都可改、不可删；自定义端点可增可删。

地址随便粘，`normalizeUrl` 补成完整请求路径——中转站的地址可能写成裸域名、带尾斜杠、
只到 `/v1`、或已经是完整路径，差一个字符就是 404，而用户看到的只有「调用失败」：

```
https://x.com                        → https://x.com/v1/chat/completions
https://x.com/v1                     → https://x.com/v1/chat/completions
https://open.bigmodel.cn/api/paas/v4 → …/api/paas/v4/chat/completions
https://relay.com/v1   (Anthropic)   → https://relay.com/v1/messages
```

判断「已经带了版本段」用的是结尾是否形如 `v\d+`，所以 `/api/paas/v4` 这种非标准版本段
也能正确处理。

## 两档：视觉与文本

| 档位 | 用途 | 默认 |
|---|---|---|
| 视觉（`Role.VISION`） | 拍照识别题号、题干、括号提示词、选项版式 | `glm-4.6v-flash`（免费） |
| 文本（`Role.TEXT`） | 分析、小方向、大方向 | `claude-opus-5` |

**两档可以是不同厂商，这是常态而不是例外**：识别天天跑要便宜，判断决定分析质量要强，
本来就很难是同一家。所以：

- 存 Key 只**补上还空着**（或没填 Key）的那一档，已经配好的一个字不动；
- 要改某一档用「只设识别档 / 只设判断档」，两档都换才点「两档都用它」。

早先存 Key 走的是无条件接管两档，于是给第二个厂商填一次 Key，
「识别走智谱、判断走 Anthropic」就被悄悄拆成两档同一家了。

识别默认挑免费模型：录入频率是系统生命线，识别不该按次心疼。
判断那一档不建议为省钱降配，它直接决定汇总是否可信。

## 模型清单发现（`core/model/ModelDiscovery`）

**目的只有一个：省得你去官网抄模型 ID。** 拉不到照样能用——内置候选和手填 ID 都在。

1. **地址试两个**：版本段下的 `/models`，以及根下的 `/v1/models`。厂商把清单挂在哪儿
   并不统一，中转站尤其乱，一个 404 不该等于「拉不到」。
2. **解析**：`{"data":[…]}`、`{"models":[…]}`、裸数组都吃；非聊天模型（向量、重排、
   语音、画图、审核）按 ID 关键字滤掉——选中它们只会得到一个看不懂的报错。
3. **视觉判定**：清单里认识的以内置清单为准，不认识的看 ID——`glm-4v` / `glm-4.6v` /
   `qwen2-vl` / 独立的 `v`、`vl`、`vlm` 段、`vision` / `omni` / `multimodal` / `ocr`。
   注意 `deepseek-v4` 这种 v 在数字**前**的判为非视觉。
4. **合并**：拉到的在前，**内置候选永远补在后面**，清单里没出现过的标成「内置候选」。
   厂商的 `/models` 不一定是全集，早先「拉到了就整份换掉」，于是拉一次清单反而把
   视觉档从候选里抹掉了——页面写着「这个厂商没有能看图的模型」，而那个模型明明调得通。
5. **自动挑选**：内置清单里推荐过的优先（顺序即优先级），陌生 ID 按命名里的档位关键字排
   ——视觉挑便宜的，文本挑强的。

拉到的 ID 缓存在本地（只缓存厂商真回过的），离线打开设置页照样有候选。
解析、视觉判定、挑选、地址归一全是纯函数，在 `logic-tests` 里有用例。

## 超时

四个都显式设，一个都不能留给默认值：

| | 秒 | 为什么 |
|---|---|---|
| connect | 30 | |
| write | 120 | 识别请求的正文是整张图的 base64，OkHttp 默认的 write 超时只有 **10 秒**，手机上传根本发不完——这是「识别超时」最常见的那一种 |
| read | 180 | 推理档想得久 |
| call | 300 | 总闸 |

超时冒到界面上是一句 `SocketTimeoutException`，看不出卡在哪一步，所以翻译成三种：
连不上服务器（检查地址和网络）、图片还没传完（少选几张或换 Wi-Fi）、模型迟迟没返回
（换个更快的模型）。

## 取正文：推理档的坑

两种协议的正文路径不同；OpenAI 兼容这一侧还要处理**推理型模型**
（DeepSeek 的 pro 档、各家 thinking 系列）：它们把思考放在 `reasoning_content`，
而 `content` 可能是空串。

判断顺序：

1. `content` 非空 → 直接用。
2. `content` 空、思考字段有内容：
   - 这次回复**被 `max_tokens` 截断**（`finish_reason == "length"` /
     `stop_reason == "max_tokens"`）且思考里连一个 `{` 都没有 → 报 `TRUNCATED`；
   - 否则把思考交上去（有的中转站确实把结构化输出放在 `content` 之外）。
3. 两处都空 → 报 `NO_BODY`（截断则同样报 `TRUNCATED`）。

这一段是从一条报错倒推出来的：界面上显示「响应中没有 JSON：我们分析题干……」
外加一大段思考。根因不是没有 JSON，而是推理档把额度全烧在思考上、正文一个字都没轮到写。
把半截思考原样交给解析层，错误就表现成一句和真相无关的话。

配套地，`Analyzer` 重试时把额度从 3072 提到 6144——第一次断在思考里，说明这道题
（多空、长句）它想得比一般题久，同样的额度再来一次还是断在同一处。

## 错误语义

| 常量 / 场景 | 说的是什么 | 该怎么办 |
|---|---|---|
| `TRUNCATED` | 额度烧在思考上，正文被截断 | 已自动用更大额度重试；总是这样就换非推理档的模型 |
| `NO_BODY` | 模型没返回正文（只有思考或空响应） | 换一个适合结构化输出的模型 |
| `$model 调用失败 <code>：<片段>` | HTTP 非 2xx，原样带回状态码与响应片段 | 中转站配错时这是唯一线索 |
| `$model 超时：…` | 见上表三种 | 按提示 |
| 拉清单失败 | 带上试过的地址、状态码，并注明**清单不是必须的** | 直接用候选或手填 ID；404 跟 Key 对不对无关 |

**「测试连接」按钮**存在的理由：地址、协议、Key 三者错任意一个，报错都长得一样。
它发一次最小请求，把原始状态码和响应片段直接摆出来。

## 两处协议差异

除了请求体形状与取值路径，只剩一条：**OpenAI 兼容端的 `temperature` 区间不含 0**
（智谱如此，多数中转站跟随），传 0 会被拒，所以客户端自动贴到下界 0.01——
尽量保住可复现性。
